Chatbot V2 Conversational Service & Human Handoff

One customer experience, two consecutive service modes. Click any component on the map to see what it owns, or play a scenario to watch a request travel through the system.

1 · Automated mode

Frontend → Dev Backend → Chatbot V2. The chatbot owns the conversation, AI reasoning, commerce actions, transcript and the ticket decision.

2 · Human mode

After a ticket is created, the bot conversation closes for good. The Dev Backend routes the customer to Zendesk, where a human agent takes over.

Where the route signal comes from

Three reads can tell the Dev Backend the route. Only two carry enough information.

Live turnconversation_closed SSE event with reason = "ticket_created".
Conversation list / reloadclosed, closed_reason and ticket from /api/v2/conversations. This is the authoritative read.
History only: not enough/api/v2/history returns closed but no closed_reason or ticket, so it cannot separate inactivity from a Zendesk handoff.

Display reference

display_reference = conversation.ticket.ticket_id ?? conversation.conversation_ref

Keep conversation_ref as the fallback even when a ticket object exists: the ticket API can report success with a payload from which no scalar ID can be extracted.

"New conversation" is a client action

  1. Frontend clears the selected session_id.
  2. First message goes to POST /api/v2/chat without session_id.
  3. Chatbot creates the session and an eight-digit conversation_ref.
  4. First SSE event is session; retain it before allowing another message.

No endpoint creates an empty conversation, so abandoned empty threads never accumulate.

Lifecycle rules

  • Default inactivity threshold is 40 minutes. Closure is lazy: it is checked on a later /chat, /history, /history/by-reference or /conversations call for that customer.
  • Inactivity is measured from the last stored V2 turn, not page reads, so polling cannot keep an abandoned conversation alive.
  • A closed bot conversation cannot be reopened through V2. A new topic starts a new session.
  • Zendesk ticket closure does not touch the bot session. It became terminal the moment the ticket was created.

Ticket outcomes

The chatbot closes only after the create-ticket API reports success. A failure or a customer "no" keeps the automated conversation open.

Boundary limitations to communicate

What the current codebase does not do, stated plainly.

  • No direct Zendesk SDK or API call exists in this repository.
  • No V2 endpoint receives Zendesk messages or ticket-status events.
  • /history holds only chatbot messages and a Boolean closed; no ticket or close reason.
  • /conversations is the authoritative V2 read for list display and reload-time routing.
  • Ticket creation closes the bot conversation immediately; Zendesk ticket closure is a later, separate event.
  • Conversations closed for inactivity must not be routed to Zendesk.
  • All of a customer's conversations share rate-limit state, because limits are keyed by customer_reference, not session_id.
